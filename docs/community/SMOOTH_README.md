# SpeedHunter 3.6.2-smooth — 完整源码与流畅度优化

## 分析结论

没有手机和仪表的实际性能日志，不能判定哪台设备的 CPU / GPU 性能不足。

现有代码可以直接证明两个软件瓶颈：

1. 3.6.1 每 100 ms 请求关键帧，只传输含 IDR 的画面，其余编码画面被丢弃。通常只有约 10 次画面更新/秒；编码器忽略即时关键帧请求时，可能只剩约 1 次/秒。传输端重复上一帧还可能使“发送包数”显得高于实际画面更新率。
2. 3.6.1 每发送 4 KB 等待 3 ms。100 KiB 帧会附加至少 75 ms 等待（未计操作系统调度、Wi-Fi 和仪表处理）。本机纯发送函数测试约 82.2 ms/帧；新版无固定等待的同类测试约 0.059 ms/帧。**这是内存写入基准，仅证明取消了软件等待，不能当作真实 Wi-Fi 帧延迟或手机/仪表跑分。**

因此，旧程序本身已足以解释不流畅，现阶段没有依据认定必须更换手机或仪表。

## 新版优化

- 默认流畅模式：保持仪表协商尺寸（用户仪表为 1024×480），H.264 连续帧，目标 20 fps / 1.5 Mbps；不支持时回退 15 fps / 1 Mbps，并保留编码器切换。
- 优先使用厂商编码器，已知 Android 软件编码器排列在后。厂商组件不保证都是硬件实现，以设备实际编码器为准。
- 不再周期性丢弃所有 P 帧。使用短 GOP（每约 250 ms 请求一次 IDR），启动/仪表重新开始/拥堵恢复时额外请求关键帧。Android 10+ 还在 Surface 输入端限制最大帧率，避免屏幕 60/120 Hz 刷新令编码器无意义超额工作；旧 Android 或忽略配置的实现不保证严格限帧。
- 去除 4 KB/3 ms 固定等待，使用最大 64 KiB 写入并由 TCP 背压及仪表拉流节奏控制。包头和原有拉流协议未改变。
- 解码顺序有界队列（4 帧）：不能直接丢一张 P 帧后继续发依赖它的帧。队列满时丢弃待发链，等待新 IDR，并主动请求关键帧恢复。
- 流畅模式不重复发送旧画面。编码器和仪表拉流控制节奏，空队列最多短等 12 ms，避免两套限帧时钟互相干扰。
- 性能区域每约 2 秒刷新：编码输出率、提交率、发送率、仪表请求频率、TCP 写入耗时、码率、队列长度/最旧帧等待时长、累计丢弃、编码器名称，以及可测时的编码输出帧龄。
- 新增移动条测试画面，区分导航 App 自身低刷新率与投屏链路问题。
- 关闭“流畅模式”后重新开始，可回退 3.6.1 的关键帧兼容路径（含原有分块等待）。这是兼容退路，通常更不流畅。

## 使用及定位方法

覆盖安装 → 仪表投屏 → 保持“流畅模式”开启 → 扫码/开始投屏 → 授予整个屏幕共享权限。

首次对比建议用“打开流畅度测试画面”，随后返回投屏页观察性能统计；切换模式必须先停止再重新开始。

| 现象 | 可得出的判断 |
|---|---|
| 手机测试画面正常，但编码率长期显著低于目标，发送跟着低 | 优先检查手机采集、编码器、资源占用或温控；不能仅据此说 CPU 不够 |
| 编码约 20 fps，发送低，仪表拉流也低，TCP 写入较快 | 仪表请求节奏或协议调度限制的可能性更大，不能等同于已测出仪表 CPU 性能不足 |
| TCP 写入明显变慢、队列积压、丢弃持续增长 | 网络或接收端形成背压；可能是无线链路或仪表接收/处理慢，当前统计不能完全分开 |
| 编码和发送接近目标，测试条在仪表仍明显卡顿 | 进一步查仪表解码/显示及缓冲；发送成功不代表已解码或显示 |
| 测试条流畅，只有导航画面卡顿 | 优先查导航 App 刷新、地图/网络数据，而非投屏 FPS |

编码输出率只统计有实际数据的输出帧；发送率只统计成功写入拉流连接的帧。兼容模式仍可能发送重复画面。帧龄在编码时间戳与系统单调时钟不匹配时显示“不可测”，不伪造延迟值。

这些是分层排查规则，**没有仪表端解码/呈现时间戳，不能直接测得仪表实际显示 FPS 或真实端到端延迟。目标 20 fps 不是实车性能保证。**

## 完整源码与构建

本压缩包提供整个 Android 工程、Java 源码、资源、Manifest、Gradle Wrapper、第三方 Go 协议源码及 GPL-3.0 许可证、Go 依赖锁定、测试和可直接使用的 ridedaemon.aar。不是仅提供差异补丁。

- 基于 RyanYuFish/SpeedHunter 的 a0bb0b925e69218d6faaacdd419f523d868ba811，加上本会话 3.6.1 独立投屏实现。
- 第三方协议库来源 https://github.com/charliecharlieO-o/ridedaemon-lib ，上游提交 d6c9294ee65a94a1632da536d0317de72dedbc40。修改后完整源码在 native/ridedaemon。
- Android：JDK 17、SDK 35、Build-tools 35.0.0、Gradle 8.7、AGP 8.6.1。用 Android Studio 导入，或运行 `./gradlew :app:assembleRelease`；Windows 用 `gradlew.bat :app:assembleRelease`。
- 依赖使用标准 Maven 仓库，需联网。国内下载不畅可用 `gradlew.bat -I tools/mirrors.gradle :app:assembleRelease`。本工程带有必需的 android.useAndroidX=true。
- `app/libs/ridedaemon.aar` 已随附。不修改 Go 代码时无需 Go / NDK；需重编原生库时使用 Go 1.25.3、NDK r27c，设置 JAVA_HOME / ANDROID_HOME / ANDROID_NDK_HOME，运行 native/build-android.sh；Windows 对应 native/build-android.ps1。
- SDK / JDK / NDK / Gradle 分发包及 Maven 全部缓存未离线打包，依赖版本已定义在工程与 go.mod / go.sum 中。
- 发布 APK 使用此前同一测试证书，可覆盖 3.6.1；源码中不包含签名私钥和机器本地 SDK 路径。自行构建默认生成自己的 debug 签名；若需替换已安装测试版，可选择另一个设备或处理签名差异。

## 验证范围

Go 协议及连续帧队列测试包含 race detector；Android 编码器测试使用 framework fakes，验证兼容回退、P 帧保留、帧率统计及 VirtualDisplay 复用。模拟测试不能代替真机射频、驱动、仪表解码/显示验证。

此前的 STANDALONE_README.md / ENCODERFIX_README.md 保留为历史设计说明；新版行为与构建以本文件为准。投屏不依赖官方 App 或 LSPosed，其他原有车辆参数 hook 功能仍按原项目工作。本次未修改车辆固件。

输入限帧依据 Android MediaFormat.KEY_MAX_FPS_TO_ENCODER（API 29+）：https://developer.android.com/reference/android/media/MediaFormat#KEY_MAX_FPS_TO_ENCODER 。KEY_FRAME_RATE 本身仅是编码速率提示，不能当作实际输入限帧。
